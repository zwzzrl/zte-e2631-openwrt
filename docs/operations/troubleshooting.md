# 典型踩坑速查

**判定**：先按下面那张速查表找现象，再跳到条目看"错前提 + 判据命令"；18 条里凡涉及刷机/槽位的，
按 [recovery.md](recovery.md) 的阶梯处理，不要临场发挥。

> 这份文件只回答一个问题：**刚才那步为什么没成，是不是我又犯了老错。**
> 每条都是"同一个动作 + 一个错前提"，换个人照做也会踩。客观限制（没实现、没资料）不在这里，
> 去 [known-issues.md](../known-issues.md)。

## 1. F · 刷机与槽位

**F1 槽位写错一格，整机变砖式回不来**
- 现象：刷完重启，链路灯正常（1000M/Full），但候选 LAN 地址裸 ARP 全无应答，断电重启无效。
- 根因：刷的是**正在运行的那个槽**，且新镜像内核区不可引导（内核从没被加载，卡在 `bootm`）。
- 正确做法：先读槽表确认活动槽，**永远刷非活动槽**；没有串口就不刷开机路径。
- 识别：`e2631-fwslot info` 看 `[running]` 与 serial；回不来时**只有串口**能区分"CRC 层起不来"
  与"内核跑起来后挂死"。救法见 [recovery.md](recovery.md)。

**F2 刷 slot1 会连带清掉两个槽内的 rootfs 与 overlay**
- 现象：刷完配置全丢，overlay 里的文件回到初始。
- 根因：rootfs 与 overlay 都在槽内，写槽即擦整段。
- 正确做法：刷前假设配置会丢，先导出；不要把"要保留的配置"放在 overlay 里当唯一副本。
- 识别：刷前 `cat /proc/mtd` 核对目标槽的槽内偏移，判断哪些分区会落在写入区间内。

**F3 把"改了开机路径"的镜像写进唯一可启动槽**（本仓真实事故）
- 现象：为了试新内核/新开机服务，直接写活动槽，重启后无网络、无串口就无解。
- 根因：把退路（另一槽）押上了；开机路径上的改动失败时没有第二次机会。
- 正确做法：要么写另一槽并先用串口确认；要么让改动**默认不生效**（pending 标记 + 首次开机窗口）。
- 识别：改动是否落在 `/etc/init.d/*`、`/etc/modules.d/*`、内核区——只要沾一个就走 F1 的流程。

**F4 设备树/分区表改了却只刷 rootfs**
- 现象：新功能不生效，或启动参数还是旧的。
- 根因：镜像的 kernel 段与 rootfs 段是两段，只换 rootfs 不会换 dtb/cmdline。
- 正确做法：整包刷；改 dts 必须整包。
- 识别：解包后比对 `root=` 与 dtb 里的分区顺序。

## 2. D · 设备与文件

**D1 mtd 是字符设备：`test -b` 恒假**
- 现象：`[ -b /dev/mtd5 ]` 永远假，脚本据此判断"分区不存在"。
- 根因：`/dev/mtdN` 是 **character** device，`mtdblockN` 才是 block。
- 正确做法：用 `test -c`；要按块读写才用 `/dev/mtdblockN`。
- 识别：`ls -l /dev/mtd5` 首字符是 `c`；`stat -c '%F' /dev/mtd5` 输出 character special file。

**D2 升级包必须是 `.bin`**
- 现象：上传 `.pkg` 被 `platform_check_image` 直接拒，提示不是合法镜像。
- 根因：校验收的是文件名后缀 + 头部魔数，`.pkg` 不在白名单。
- 正确做法：出厂/发布一律 `.bin`；内部工作名可以叫别的，交付前改名。
- 识别：`head -c 16 <file> | xxd` 看魔数，并确认后缀是 `.bin`。

**D3 盒上没有 `sftp-server`，`scp` 必失败**
- 现象：`scp` 卡住或 `subsystem request failed`。
- 根因：dropbear 不带 sftp 子系统。
- 正确做法：用 `ssh … 'cat > /tmp/x'` 或 `tar -cf - … | ssh … 'tar -xf -'` 管道。
- 识别：`ssh <box> 'ls /usr/lib/ssh/sftp-server'` 报 not found。

**D4 用没解包的旧目录当"根文件系统里有什么"的答案**
- 现象：报告某个文件存在/不存在，事后发现看的是上一轮残留。
- 根因：检查脚本只读固定目录、从不解包，回答的是上一次的内容。
- 正确做法：每次先解包到新目录再查；答案必须来自本轮刚解出来的树。
- 识别：检查脚本里有没有"解包"这一步；`find <dir> -newer <镜像>` 是否为空。

## 3. C · 命令与工具

**C1 `iperf3 --cport` 钉不住五元组**
- 现象：想固定源端口让硬件流表命中，结果流量还是走软件栈/走了另一条路。
- 根因：**控制连接**先建立，它的临时端口先被流表学走，数据连接复用不上。
- 正确做法：让客户端**绑定**源地址/端口（或先建连再指定同一端口），并核对流表里学到的五元组。
- 识别：抓包看第一个 SYN 的源端口是不是你以为的那个；`conntrack -L` 里的五元组与预期比对。

**C2 `sleep` 与 `pkill -f` 在本项目禁用**
- 现象：脚本里等待/清理进程的写法被拒或行为不可预期。
- 根因：`sleep` 占住会话且期间观察不到任何东西；`pkill -f` 按整条命令行匹配，会误杀同名的 shell/编辑器。
- 正确做法：用轮询（`while` + 读状态文件/`uptime`）代替等待；用 pid 文件或 `kill <pid>` 精确杀。
- 识别：脚本里出现 `sleep`/`pkill -f` 即为违规；换成"读一次状态，变了就继续"。

**C3 `B(){ ssh … | tr -d '\r'; }` 的返回码是 `tr` 的**
- 现象：远端命令失败，函数却返回 0，判断分支永远走"成功"。
- 根因：管道返回最后一段的退出码。
- 正确做法：`set -o pipefail`，或把远端输出先落到变量再 `tr`，并显式检查 `ssh` 的 `$?`。
- 识别：故意让远端 `false`，看函数返回码是否非 0。

**C4 拿"某条命令没输出"当"没发生"**
- 现象：判"计数器没涨"，其实那一路绕过了计数器。
- 根因：计数器有盲区（裸调用绕过自增、整表 memset 清零）。
- 正确做法：至少两条独立证据（计数器 + 抓包/对端计数）；"计数为 0"只写"未见计数"，不写"未发生"。
- 识别：查该计数点的自增是否只在一个函数里、是否有 memset。

**C5 XPS/`echo 1 > xps_cpus` 是空操作**
- 现象：调 XPS 的 A/B 测不出差别，以为结论是"XPS 无用"。
- 根因：单发送队列下该 sysfs 节点不可写（读回 `ENOENT`），写入被忽略。
- 正确做法：写前读一次确认可写；不可写就把这段从脚本里删掉，别留着当"已调优"。
- 识别：`cat /sys/class/net/lan1/queues/tx-0/xps_cpus`；写后立刻读回比对。

## 4. S · 串口与会话

**S1 串口 `reboot` 后停在 login banner，后续命令被吞**
- 现象：发 `reboot` 后继续发命令，全无回显；以为"卡死了"。
- 根因：重启后串口上出现 login banner，输入落在 banner 的提示行，被 getty 吃掉。
- 正确做法：`reboot` 后先等 banner 稳定，回车一次确认拿到 shell 提示符，再发命令；判活优先用网络侧证据。
- 识别：串口输出里出现 `login:` 或 banner 那段 ASCII；发一个 `echo MARKER`，看不到 MARKER 就是没进 shell。

**S2 串口是独占资源**
- 现象：两个会话同时开，输出互相插花、命令丢字符。
- 根因：同一 tty 多写者。
- 正确做法：任何时刻只开一个串口会话；交接时把"当前会话状态"写进交接文档。
- 识别：`fuser <serial-dev>` / `lsof <serial-dev>` 看有没有第二个持有者。

## 5. K · 内核与模块

**K1 `kexec` 之后 `/tmp` 是全新 tmpfs**
- 现象：kexec 起来后，之前放在 `/tmp` 的脚本/镜像/日志全没了，自动化链路断在第一步。
- 根因：`/tmp` 是 tmpfs，随内核实例重建。
- 正确做法：跨内核传递的东西放持久分区（overlay 里），或在新内核里重新下发。
- 识别：kexec 前后各 `cat /proc/uptime` 与 `ls /tmp`；`uptime` 归零即新实例。

**K2 模块参数动过没还原**
- 现象：隔天复现同一实验，数值差一大截，找不到原因。
- 根因：上一轮 `insmod … ipv6=1` 之类的参数没恢复默认，后续所有数字都在非默认配置下取得。
- 正确做法：每轮实验开始与结束各 dump 一次生效参数（`/sys/module/*/parameters/*` 或 debugfs），并写进记录。
- 识别：`cat /sys/module/<mod>/parameters/*` 与文档的"默认值"逐项比对；不一致就是脏态。

**K3 `kexec` 不复位芯片**
- 现象：换了内核，行为还是怪，怀疑新内核有 bug。
- 根因：寄存器/硬件状态跨内核存活，`rmmod` 也清不掉。
- 正确做法：怀疑脏态优先，做一次真复位（断电/刷槽冷启）再比。
- 识别：同一镜像"冷启"与"kexec 起"结果不同 ⇒ 先判脏态，不要先判代码。

## 6. M · 测量与判读

**M1 不能用 v4 流量当"盒子活着吗"的探针**
- 现象：v4 ping/吞吐"双冻结"，据此判盒子死了，实际它活得好好的。
- 根因：v4 走硬件 flow offload，不经过 CPU 栈；offload 路径的计数与软件路径的冻结互不代表。
- 正确做法：判活用**管理面**证据（`/proc/uptime`、SSH 会话、串口）；吞吐用"对端计数"而不是本机软件计数。
- 识别：`/proc/net/dev` 不涨但 `uptime` 在涨 ⇒ 是 offload 生效，不是死机。

**M2 测试机插错口，所有症状都能自洽**
- 现象：改完 VLAN/端口布局后"只收不发"，怎么改都复现。
- 根因：测试机实际在 lan1，而记录说在 lan2；回复从真正的 WAN 口走了。
- 正确做法：每次换布局先做**双向**端口计数验证（发包前后读四个口的 `rx_packets`）。
- 识别：发 40 个广播帧，看哪个口 +40；对不上的那个就是真位置。完整案例见本文附录。

**M3 拿错仪器扫时间常数**
- 现象：按某个"边界秒数"去扫一个旋钮，一个数都读不到。
- 根因：边界对应的是**另一个**旋钮（例如驱动老化 vs 硬件 aging），扫错对象。
- 正确做法：先读源码确认这个常数由谁定义，再用对应仪器；时间常数"对得上"只说明量级像，不构成因果。
- 识别：扫之前先在源码里找到该常数的定义与生效条件（`grep` 默认值 + 日志里它被打印的那一行）。

**M4 小样本 + 污染环境得出的"结论"**
- 现象：两个臂差 30 %，复测又反过来。
- 根因：环境里还有另一个故障（停顿/丢包）在同时起作用。
- 正确做法：先做环境体检，再比两个臂；一轮只改一个变量。
- 识别：同配置重复 3 次，极差 >10 % 就先别下结论。

## 附：案例复盘 —— 端口认错导致「只收不发」（`wanport-tx-deaf-2026-10-30.md` 已并入本文件，原文件删除）

## 「任意口当 WAN 之后只收不发」是一次误判（2026-10-30 晚推翻）

> 这条曾经的"bug"不成立：**驱动没有 bug，VLAN 表写成 0 也不会掐死发送方向。**
> 出事那轮实验里测试机插在 **lan1**，而布局假设它插在 lan2 —— 把端口认错之后，
> 每一个观察到的"症状"都能用"回复从真正的 WAN 口走了"解释干净。
> 本文记录证据链、当初为什么会被骗，以及以后怎么在 30 秒内确认测试机到底插在哪个口。

### 1. 结论

| 曾经的说法 | 现在的事实（都是本轮实测） |
|---|---|
| 端口被移出 br-lan（`members == 0`）后，盒子发不出帧 | **发得出去**。WAN 切到 lan1 并重启后，主机（就在 lan1 上）ping 3/3、ssh 正常、盒子反向 ping 4/4，抓包双向可见 |
| 根因是 `zx_sw_apply()` 在 `members == 0` 时把 VID 1 表项写成 0 | **不成立**。在跑着的独立 WAN 布局上直接把 `vlan[1]` 写成 0，双向收发照旧（§4） |
| 该改法已进驱动 | **已回退**，恢复上游语义（`members ? vlan \| VALID : 0`） |

### 2. 怎么发现端口认错了

在 `br-lan = {lan1, lan3}`、`lan2` 独立这种布局下，给 lan1 发 40 个**广播帧**
（ethertype 0x0806 / 0x0800 / 0x86dd / 0x88b5 各 10 个），然后读四个口的收包计数：

```
发帧前: lan1 321  lan2 302  lan3 0  wan 0
发帧后: lan1 361  lan2 316  lan3 0  wan 0     ← 40 帧全部落在 lan1
```

**lan1 +40，lan2 一动不动。** 测试机 `<宿主网卡>` 接的是 **lan1**，不是之前记录的 lan2。
用不同 ethertype 分别发，可以排除"某种协议被 ACL 丢掉了"这一层解释——四种类型的都走 lan1。

### 3. 用正确端口复测：独立 WAN 口收发都通

```sh
## 盒子上（串口或 ssh）：把 WAN 切到测试机所在的 lan1，然后重启
e2631-wanport apply lan1 --force && reboot
```

起来后的现场（`uci show network` + `ip addr`）：

| 对象 | 值 |
|---|---|
| `network.wan.device` | `lan1` |
| `lan1` | `<实验路由器地址>/24`、`fd00:aa::1/64`、`fe80::e660:4dff:fe86:71f0/64`（WAN 固化 MAC `e4:60:4d:86:71:f0`） |
| `br-lan` | `192.168.1.1/24`，成员 `lan2 lan3 wan` |
| `sw_members` | **0x0**（br-lan 里只有 lan2 一个口有链路，算不出硬件交换同伴，符合预期） |

测试机 `<实验主机地址>/24` + `fd00:aa::2/64` 侧的结果：

| 方向 | 命令 | 结果 |
|---|---|---|
| 主机 → 盒子 | `ping -c3 <实验路由器地址>` | **3/3**，`lladdr e4:60:4d:86:71:f0` |
| 主机 → 盒子 | `ssh root@<实验路由器地址>` | 通，`uname -r` = 6.18.55 |
| 盒子 → 主机 | `ping -c4 -I lan1 <实验主机地址>` | **4/4**，`lan1 tx 15 / rx 25` |
| 主机侧抓包 | AF_PACKET 计数 | 盒子发了 4×0x800 + 1×0x806，主机回了 4×0x800 + 1×0x806 |

也就是说：**一个不在任何网桥里的独立口，收发都正常**，`members == 0` 不影响它的发送。

### 4. 直接证伪"VLAN 表写 0 会掐死发送"

在这一布局（已经能正常通信）下，用寄存器工具把 VID 1 表项改写成 0 —— 也就是当初
怀疑的"罪魁祸首"那个值：

```sh
/tmp/zxtool vlan 1 00000000 00000000 00000000 00000000   # 写 0
ping -c3 <实验主机地址>          # 盒子 → 主机：3/3
## 主机 → 盒子：ping -c3 <实验路由器地址> 也是 3/3
```

双向照旧。再把它改回驱动实际写的值（全端口 untag + VALID = `0xaa9`），同样正常。
所以 VLAN 表项内容不是原因，两个方向都通。



### 5. 当初那些"证据"为什么看起来成立

出事那轮的现场是：`e2631-wanport apply lan2 --force` + 重启，配置层面 `wan device = lan2`、
`lan2 = <实验路由器地址>/24`；测试机配 `<实验主机地址>/24` 却插在 **lan1** 上。于是：

| 当时的观察 | 真实原因 |
|---|---|
| 主机 ping 盒子：ARP 拿不到，`No route to host` | 主机的 ARP 请求进了 br-lan；盒子给 `<实验路由器地址>` 的 ARP 应答按路由从 **lan2** 发出（那口上是另一台机器），主机永远收不到 |
| `lan2` 的 `rx_packets` 在涨、`tx_packets` 不动 | 涨的那点计数是背景流量；主机帧根本不在 lan2 上（§2 的对照测试能一眼看穿） |
| 盒子 ping 自己的 LAN 对端（桌面）也失败 | 桌面那轮是否在线没有独立验证过，不能算证据 |
| `sw_members = 0x0` | **正常**。br-lan 里只有 lan2 一个有链路的口，算不出"两个口同桥"，硬件交换本来就该关 |

三条教训，写进流程：

1. **每次动网络布局之前，先确认测试机在哪个物理口**（§6 的做法，30 秒）；
2. 端到端不通时，先分清"帧没发出去"和"帧发到别的口去了"——两者的处置完全不同；
3. `sw_members`、MAC MIB 这类计数只能当"有没有动作"的旁证，不能单独当"帧上没上线路"的证据。

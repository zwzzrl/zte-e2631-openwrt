# E2631 flash 布局（128 MiB 整片）

**判定**：这颗板子的 flash 是 **A/B 整机双槽**（各 28 MiB，每槽带一份完整内核 + 一份 rootfs），
尾部另有 17 MiB 预留的国内插件区，两者**零交集**。分区偏移只能来自"内核内建分区表"或"整片
dump 逐字节比对"两个来源 —— `/proc/mtd` 只有尺寸与名字、**没有偏移列**，按尺寸累加必然算错
（历史上因此造出过"槽 B 与插件区重叠 12.75 MB"的假坐标）。

---

## 1. 权威数据源与它在哪里

| 证据 | 位置 | 说明 |
|---|---|---|
| 内核内建分区表 | vmlinux 文件偏移 `0x432358`，15 条，步长 `0x20` | `{char *name; u32 pad; u64 size; u64 offset; u64 pad;}`；name 指针 = `0xC0008000 + 字符串在 vmlinux 里的文件偏移` |
| 官方升级包头 | 包内 `0x60`（槽 A）/ `0x70`（槽 B） | `base`/`span` 与内核表逐字段一致，两条独立证据互咬 |
| 整片 dump | `e2631_no_oob.bin`，134,217,728 B，md5 `0a7cae9b6504d6568d2bc4d795e6f7c0` | 是 **V1.0.0.6B5.8000（2024-09-25）**，别当 8B8 用 |
| 真机 `hexdump` | `/dev/mtdblockN` 按偏移读 | 定案靠"整片 dump ↔ mtd 视图"逐字节相同 |

vmlinux 从哪来：`kernel1` 分区 = `[0x20 槽头][uImage 64 B][zImage][追加 DTB]`；zImage 内
`0x65A8` 处是 gzip 流（wbits=47），解开得 **6,667,040 B（0x65BB20）** 的 ARM Image，
load base `0x40008000`。

## 2. 全片分区表（内核表 + 字节实测定案）

| 分区 | 物理基址 | 尺寸 | 依据 |
|---|---|---|---|
| Bootloader | `0x00000000` | 1.00 MB | 内核表 |
| tag | `0x00100000` | 1.00 MB | 内核表（MAC/SN/板级参数） |
| wifi | `0x00200000` | 1.00 MB | 内核表（MT7916/7976 校准数据） |
| usercfg | `0x00300000` | 2.00 MB | 内核表 |
| defcfg | `0x00500000` | 2.00 MB | 内核表 + 明文比对（**mtd5，禁写**） |
| kernel1（槽 A） | `0x00700000` | 28.00 MB | 内核表 + 槽头实测 + 包 verhdr |
| kernel2（槽 B） | `0x02300000` | 28.00 MB | 同上 |
| rootfs | — | — | 占位符 `(0,0)`：rootfs 在**每个槽内部** |
| UNIFIED | `0x06E00000` | 1.00 MB | 内核表 + 字节命中 |
| UUPlugin | `0x06F00000` | 5.00 MB | 内核表 + 字节命中 |
| DPIPlugin | `0x07400000` | 3.00 MB | 内核表 + 擦除态一致 |
| JDXBPLUGIN | `0x07700000` | 1.50 MB | 内核表 + 擦除态一致 |
| owdptsbin | `0x07900000` | 0.625 MB | 内核表 + 字节命中 |
| status | `0x07A00000` | 5.00 MB | 内核表 + 擦除态一致 |

插件区预留 `0x06E00000`–`0x07F00000`（17 MB），6 个分区实际占 16.125 MB；区内空隙
`0x07880000`–`0x07900000`（512 KB）、`0x079A0000`–`0x07A00000`（384 KB），尾端
`0x07F00000`–`0x08000000`（1 MB）未用。

## 3. 槽内几何（每槽 28 MiB，两槽只差基址）

```
槽 A  基址 0x00700000          槽 B  基址 0x02300000
+0x000000  槽头 0x20 B          +0x000000  同左
+0x000020  uImage 头 64 B       +0x000020  同左
+0x000000  内核区 0x340000      +0x000000  内核区 0x340000   → B 绝对 0x2300000
+0x340000  rootfs 0x1220000     +0x340000  rootfs            → B 绝对 0x2640000
+0x1560000 版本头 0x20000       +0x1560000 版本头            → B 绝对 0x3860000
```

- 槽跨距校验：`0x2640000 − 0xA40000 = 0x3860000 − 0x1C60000 = 0x1C00000` ✓
- 槽头 16 字节（两槽相同、逐代相同）：`33 33 33 33 CC CC CC CC 88 88 88 88 DD DD DD DD`，
  其后 `FF FF FF FF`。
- uImage 头（`+0x20`）：魔数 `27 05 19 56`，`load == entry == 0x40008000` —— **两槽内核的
  加载/入口地址完全相同，不同的只有 flash 存储偏移**。
- 实测内核大小：6B5 = 3,342,678 B；8B8 = 3,356,582 B；09-21 那台 = 3,361,806 B。
  内核之后到下一个 128 KB 擦除块边界之间是填充，`0x340000` 起才是 rootfs。
- rootfs 尺寸**随固件代变化**：6B5 = `0x1100000`、7B5/8B8 = `0x1220000`；版本头位置随之移动，
  **不是常量**。8B8 上 `0x20A0000` 实测为全 FF，说明该代版本头不在 6B5 那个位置。
- 版本头（verhdr）内容：`+0x8`/`+0xC` = `key1`/`key2`（与升级包头里的 key 对一致），
  可打印串如 `"V1.0.0.6B5.8000"`、`"ZXHN E2631 V1.0.0"`、构建时间戳 `20240925150510`。

## 4. `/proc/mtd` 的"同名不同层"

`/proc/mtd` 里 `kernel1`、`kernel2`、`rootfs` 三行**不是**按物理顺序平铺的三个区间，而是：

| 名字 | 在槽层表里指 | 在 `/proc/mtd` 里指 |
|---|---|---|
| kernel1 | 槽 A 整段（28 MiB @ `0x700000`） | 槽 A **槽内**那份内核（3.25 MiB） |
| kernel2 | 槽 B 整段（28 MiB @ `0x2300000`） | 槽 B **槽内**那份内核（3.25 MiB） |
| rootfs | 占位符 `(0,0)` | **活动槽**槽内那份 rootfs（18.125 MiB） |

⇒ 引用"某个分区叫什么"之前，先问一句：**这是哪张表里的名字、这张表是哪一层？**
拿 `/proc/mtd` 的名字顺序推物理顺序，前提本身就不成立。

## 5. rootfs 在 flash 上是 AES-128-ECB 密文

- 原厂内核在 MTD/SPI-NAND 读路径上做透明解密：**flash 是密文，`/dev/mtdblockN` 是明文**。
  所以"jffs2 能挂载"只证明 mtd 视图是明文，不能证明 flash 原始字节是明文。
- AES-128-ECB，key `E263111559d0dfde`（16 B ASCII，由原厂内核 `zte_token` 派生）。
- rootfs 基址 = `0xA40000`（不是旧记的 `0xD80000`）：`raw@0xA40000` 解密后得
  `85 19 01 e0 31 00 00 00`，与设备 `mtdblock` 视图逐字节一致。`0xD80000` 落在 rootfs
  **内部**，解密后同样得到一个"看着像 JFFS2 节点"的头 ⇒ **"解出合法 magic / 熵值高"都不足以
  判定分区基址**，只能用 mtd 视图 ↔ 整片 dump 的逐字节比对来定。
- 插件区（`0x6E00000` 之后）是**明文** JFFS2，无需解密。`wifi` 分区也是明文 JFFS2
  （首 1 MB 约 343 个节点），校准数据可以直接 `ls` 读。

## 6. 能不能回收：给 OpenWrt 的可用空间

| 区间 | 大小 | 依据 |
|---|---|---|
| `0x3F00000`–`0x6E00000`（中部） | 47.00 MB | 逐 128 KB 块扫描，非擦除块 0 个 |
| `0x7F00000`–`0x8000000`（尾） | 1.00 MB | 内核表推到 `0x7F00000` |
| 槽 A 尾 `0x1C60000`–`0x2300000` | 6.625 MB | 版本头之后全 FF |
| 槽 B 尾 `0x3860000`–`0x3F00000` | 6.625 MB | 同上 |
| 插件区内空隙 | 0.875 MB | 见 §2 |
| 合计 | ≈62.1 MB | |

对刷机的影响：

- 不动槽 A（`0x700000` 与 `0xA40000` 两处）就保留完整原厂固件，是唯一的退路。
- 把 OpenWrt 的 rootfs 写进槽 B 的 rootfs 区（`0x2640000`）会覆盖原厂那份备份镜像，
  原厂"两槽互为备份"就只剩槽 A。想两全：**内核放槽 B、rootfs/overlay 放中部 47 MB**。
- `mtd5`（defcfg）**永久禁写**，基线 sha256 见 [flashing.md](../operations/flashing.md)。

## 7. 怎么复核（可执行）

真机（无 `dd`，用 busybox 前缀 + `hexdump -s`，只读）：

```sh
busybox hexdump -C -s $((0x700000))  -n 64  /dev/mtdblock0   # 槽 A 槽头
busybox hexdump -C -s $((0x2300000)) -n 64  /dev/mtdblock0   # 槽 B 槽头
busybox hexdump -C -s $((0x6E00000)) -n 32  /dev/mtdblock0   # 对 mtdblock13@0
busybox hexdump -C -s $((0x7400000)) -n 32  /dev/mtdblock0   # 对 mtdblock12@0
busybox hexdump -C -s $((0x7700000)) -n 32  /dev/mtdblock0   # 对 mtdblock14@0
busybox hexdump -C -s $((0x7A00000)) -n 32  /dev/mtdblock0   # 对 mtdblock11@0
```

离线：解开 zImage 里的 vmlinux 后，从 `0x432358` 起按 `0x20` 步长解析 15 条表项，
再把表声明的落点与整片 dump 的字节对一遍。

**判据**：表里每条都要有"内核表声明"与"至少一处内容比对"两条证据；只有 `FF↔FF` 一致的条目
（DPIPlugin/JDXBPLUGIN/status）必须与已命中的条目联合，才能算闭合。

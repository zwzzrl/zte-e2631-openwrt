# AX-02 判负：`ZX_TX_QUEUE_LIMIT=256` 不是当前瓶颈

> 日期：2026-11-02。范围：ZXHN E2631（ZX279128S）自研固件的发送侧限流与 v6 FFE 快路。
> 结论性质：静态源码 + 既有实测数据回代 + BDP 算式；本文**没有新上机**、没有改码。
> 口径：源码行号来自本仓 HEAD `2dab71d`；盒子交付态是 P10.5（`623a812`）。
> 缩写：`SRC/` = `overlay/target/linux/sanechips/files/drivers/net/ethernet/zte/`；文中未写目录的 `zx279128s-*.c` 均指 `SRC/`。

## §0 结论

**`ZX_TX_QUEUE_LIMIT=256` 限的是「已提交硬件、尚未回收的帧数」`tx_pending`（并兼作 `ndo_start_xmit` 的
busy 判据），不是 skb 队列长度，也不是描述符数；在当前工作点它没有咬住，AX-02 方向判负。**

1. **机制**：`tx_pending` 在提交时 +1（`zx279128s-main.c:1854`），`zx_tx_reclaim()` 按硬件完成数减
   （`zx279128s-main.c:1196-1203`）；`>= 256` 时快路在 `zx279128s-accel.c:2985-2995` 返回
   `ZX_FFE_V_QFULL` 回栈，栈路径在 `zx279128s-main.c:1910-1914` 返回 `NETDEV_TX_BUSY` 让 qdisc 重排。
   **超限不丢帧**；环外是 fq_codel，上限 10240 帧 / 4 MB（原始记录（未入库）
   核对过 `sch_fq_codel.c:514-519`）。见 §1。
2. **数值**：`256 × 1514 = 387,584 B = 3.10 Mbit`。在实测 RTT 3.25–3.38 ms 下对应
   **917–955 Mbit/s**——比 v6 实测 748 高 22%，与 v4 的 926 只差 1%（§2）。
   要让 256 卡住 748，RTT 需要 4.15 ms，实测只有 2.8–3.4 ms。
3. **工作点**：当前在途 **180–213 帧**、`fallback_qfull` **恒 0**、300 s 单流峰值 **207/256**（81%）。
   余量只有约 20%，但**没有撞顶**（§2）。
4. **不该调**：按无排队 RTT 2.00 ms 只需 **175 帧** ⇒ 256 已经是 **1.46×BDP**。
   **硬上界 1024 = `ZX_NUM_TX_DESC`**：`tx_bp[]` 按 1024 分配（`zx279128s-main.c:3754-3757`），
   `>1024` 才会覆盖在飞描述符（§3）。
5. **战略含义**：v4 926 走 PPE 硬件（CPU 不碰帧），v6 748 走 FFE 软件逐帧 ⇒ 20% 差距
   **更可能来自「v6 没有硬件路径」**，而不是队列上限；这一条是假说，**未证**（§4）。

## §1 这个常量到底是什么

- 定义：`zx279128s-eth.h:257` `#define ZX_TX_QUEUE_LIMIT 256`；同头 `zx279128s-eth.h:256`
  `#define ZX_NUM_TX_DESC 1024`、`:268` `ZX_DESC_SIZE 16`。
- 计数量：`adapter->tx_pending`（`zx279128s-eth.h:783`，u32）。提交时 +1（`zx279128s-main.c:1854`），
  `zx_tx_reclaim()` 按硬件完成数减（`zx279128s-main.c:1196-1203`）。**一帧一描述符**
  （`zx279128s-main.c:1835` `tx_idx = tx_cur_idx % ZX_NUM_TX_DESC`），所以数的是**包**不是字节；
  每帧上限 1536 B（`zx279128s-main.c:1896` 丢 >1536）。
- **7 处使用点**（全目录 grep 只有这些）：

| # | 位置 | 动作 |
|---|---|---|
| 1 | `zx279128s-accel.c:2985` | 快路 #19：满 → `return ZX_FFE_V_QFULL`（`:2995`）→ 回栈；`fallback_qfull` 在 `:3203-3206` 计数 |
| 2 | `zx279128s-main.c:1242-1248` | reclaim：`pending < limit` 才 `netif_wake_queue()`，且唤醒全部 5 个端口 |
| 3 | `zx279128s-main.c:1826-1827` | `zx_tx_submit_bp()` 入口：`>= limit` 直接 `return false`，一个字节都没写 |
| 4 | `zx279128s-main.c:1868-1874` | 提交成功后 `>= limit` → `netif_stop_queue()` 所有端口 + `zx_tx_kick()` |
| 5 | `zx279128s-main.c:1910-1914` | 栈路径满 → `NETDEV_TX_BUSY`（qdisc 重排，不丢） |
| 6 | `zx279128s-main.c:2666` | NAPI poll 里 reclaim 后仍满 → 再 arm 定时器 |
| 7 | `zx279128s-main.c:3332` | `txtest` 调试口 `pending + ndesc > limit` 才 `break`（不发） |

- **一句话归类**：它是 `tx_pending` 计数（不是 skb 队列长度、不是描述符数），并被当作
  `ndo_start_xmit` 的 busy 判据用（`zx279128s-main.c:1910` → `NETDEV_TX_BUSY`；
  `zx279128s-main.c:1868` → `netif_stop_queue`）。
- **限制「包」不限制「字节」**：驱动没有字节记账。
  - 典型满帧 1514 B：`256 × 1514 = 387,584 B = 378.5 KiB = 3.10 Mbit`；
  - 最大帧 1536 B：`256 × 1536 = 393,216 B`；
  - 只算 TCP 载荷 1440 B：`256 × 1440 = 368,640 B`；
  - 反方向 ACK 帧（60 B）也占同一批槽——一个适配器只有一个发送环、5 个端口共用
    （`zx279128s-main.c:1865`「快路与栈共用一个环」、`:1842` 每帧按 `ZX_PORT_TX_QUEUE(eport)` 定向、
    `:1868-1873` 一满就停所有端口），所以**有效数据槽 < 256**。
- **不是环深**：环 1024 槽是硬上限（`zx279128s-eth.h:256`），256 是软水位，`>=` 就停队，环永远到不了 1024。
- **不是 TCP 窗口**：超限不丢——快路回栈、栈路径 `NETDEV_TX_BUSY` 重排，环外 fq_codel 10240 帧。

## §2 数值：256 在当前 RTT 下卡不住 748

两个恒等式（所有判读都靠它）：

- 在途数据帧 **`N = T(Mbit/s) × RTT(ms) / 12.112`**（12.112 = 1514 × 8 / 1000）；
- 若 256 是硬上限：**`T_cap = 256 × 12.112 / RTT(ms)`**。

| RTT (ms) | 2.808 | 3.246 | 3.38 | **4.15** | 9.0 |
|---|---|---|---|---|---|
| `T_cap` (Mbit/s) | 1104 | 955 | 917 | **748** | 344 |

已有 v6 数据回代（原始记录未入库）：

| 吞吐 (Mbit/s) | RTT (ms) | 在途 `N` | 占 256 |
|---|---|---|---|
| 777.4 | 2.808 | **180** | 70% |
| 796.5 | 3.246 | **213** | 83% |
| 748 | 3.38（ping 中位） | **209** | 82% |

- 三个 v6 点都只有 256 的 70–83%；**要让 256 卡住 748，RTT 必须 4.15 ms，实测只有 2.8–3.4 ms**
  （原始记录未入库）。
- 300 s 单流 ffe 747.6 Mbit/s（min 575 / max 901）、`qlen_peak=207`、`fallback_qfull=0`
  （原始记录未入库）。
- 对照组 v4 937.9 Mbit/s @6.54 ms → N=506，但 v4 走硬件、不进这个环，**不能拿来否定 256 对 v6 的限制**
  （原始记录未入库）。

## §3 该不该调：不该；硬上界 1024

- **最便宜的判别阈值**（原始记录未入库）：若 256 咬住，应同时看到
  `Δfallback_qfull > 0`、`q` 贴 256、`N = T × mean_rtt / 12.112 > 230`。当前三项全部不成立
  （`qfull=0`、峰值 207、在途 180–213）。
- **无排队口径**：`RTT_min = 2.00 ms`（原始记录里的空载 ping 中位）、
  `T_max = 926`、`avg = 1325 B`（ACK 约占 13%），
  `1.14 × 926 × 2.0 / 12.112 ≈ 175` 帧 ⇒ **256 已是 BDP 的 1.46×**，不该调
  （原始记录未入库）。
- **只有出现反证才调**：宿主 `netem` 把 RTT 抬到 ~9 ms，60 s 内 `q` 钉 256 / `fallback_qfull` 涨 /
  吞吐落到 330–352 Mbit/s（三者互斥，一次定方向）。若真钉住，第一档 384、再 512，
  **绝不能 >1024**（同文件 §3.3、§4）。
- **硬上界 1024 = `ZX_NUM_TX_DESC`**（`zx279128s-eth.h:256`）：全目录没有按 256 固定分配的数组；
  `tx_bp[]` 按 `ZX_NUM_TX_DESC` 分配（`zx279128s-main.c:3754-3757`）、按 `% ZX_NUM_TX_DESC` 索引
  （`zx279128s-main.c:1835`）；`>1024` 会覆盖在飞描述符 + 破坏 bp 所有权
  （原始记录未入库）。
- **副作用**（若将来真调）：队列本身最多贡献 256→3.34 ms、384→5.0 ms、512→6.7 ms、1024→13.4 ms 的时延；
  每个在飞帧钉一个 2048 B 的 BMU 槽（池子 4096，与 RX 共享），256→6%、1024→25%
  （原始记录未入库）。

## §4 战略含义：20% 差距更像「v6 没有硬件路径」

- v4 实测 926–938 Mbit/s，走 PPE 硬件（`accel_ipv4` 首行为 `hw`），CPU 不碰帧；v6 实测 748 Mbit/s，
  走 FFE 软件逐帧。旁证：v4 10 s / 100 Mbps 只让 `consumed +34`、`30: +23`；v6 同条件
  `consumed +120641`、`30: +2972`（原始记录未入库）。
- 因此 20% 差距**更可能**来自「v6 没有 PPE 那样的硬件路径」，而不是 256 的队列上限
  （原始记录（未入库） 矛盾 3）。
  **〔2026-11-03 撤回：这句作废，不要再引用。〕** 原厂 v6 的 918–928 Mbit/s **同样是在 CPU 上跑
  FFE 逐帧**——NPU 表项装得上、数据面却 `hit:0`，帧是 CPU 的 FFE 软快转送出去的〔原厂二进制 +
  本板实测：[vendor-ipv6-behavior.md](../reverse/vendor-ipv6-behavior.md) §8.4「数据面没交给硬件」
  与 §8.5「功劳在 FFE，不在 ASIC」〕。所以「v6 没有硬件路径」解释不了这 20%：**原厂也没有 v6
  硬件路径**，差距只能在 CPU 侧 FFE 的**实现细节**里找——现有材料里最像的一条是发送队列结构
  （原厂 FFE 私有 napi + per-CPU 队列 vs 我方五口共享环 + `tx_lock` + 每描述符一次门铃，见
  [zero-copy.md](zero-copy.md) §五），但**具体原因仍未定**，不许把这条候选写成已定论。
  按此，本文件 §0 第 5 条与本小节标题里的同一句**一并撤回**（原句保留，不改写）。
- 这一条是**假说**：现有材料没有做「v6 走硬件」或「CPU 逐帧开销拆解」的对照，**待裁决**。
  即便把 256 调大，v6 仍是软件逐帧路径，不会因此获得硬件卸载。

## §5 边界与没做的事

- **没有新上机**：本文数字全部来自既有轮次（原始记录未入库），
  没有 ssh / 串口 / 跑流 / 改码 / 构建。
- **`-w` 不能当「加大在途」的旋钮**：本机 `net.core.wmem_max=212992`，`iperf3 -w ≥512K` 直接被拒
  （原始记录里的实测）。要强制 BDP 只能用宿主 `netem` 抬 RTT；
  该实验本轮 **0 轮**，所以「判负」建立在机制 + 实测工作点，不是强制 BDP 实验。
- **盲区**：栈路径撞 256 只返回 `NETDEV_TX_BUSY`（`zx279128s-main.c:1910-1914`），没有计数器；
  `fallback_qfull` 只覆盖快路 #19（`zx279128s-accel.c:3204`）⇒「stack 臂撞满」这件事本文看不见。
- `qlen_peak` 开机累计、无清零口（`zx279128s-main.c:1866-1867`）；143 与 207 是**两个 boot**，不能互相证否。
